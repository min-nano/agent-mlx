# 設計ノート — なぜこの形なのか

このリポジトリの**設計の根拠**をまとめた文書です。「何がどこにあるか」ではなく
「なぜそこに置いたか」を書いています。読み手は、このコードを触る人間と AI の
両方を想定しています（`CLAUDE.md` は Claude Code への**規則**に絞ってあり、
理由はこちらに集めてあります）。

- 使い方 → [README.md](../README.md)
- 作業時の規則 → [CLAUDE.md](../CLAUDE.md)

## 1. 何を確かめたいアプリなのか

Apple の **MLX** で、iPhone と Mac の上にローカル LLM を載せて動かします。作った
動機は「MLX が実機でどれくらい動くのかを自分の手で確かめたい」でした。

この動機が設計をひとつ決めています。**速度の数字を、答えと同じ重みで扱う**という
ことです。応答ごとに tok/s・TTFT・プロンプト処理速度・GPU メモリのピークを表示し、
会話と一緒に保存し、ベンチマークを（おまけではなく）独立した画面と CLI サブ
コマンドとして持っています。「動いた」だけでは知りたいことが分からないからです。

## 2. 全体像

```
┌─────────────────────────────────────────────────────────────┐
│ Sources/            SwiftPM パッケージ・外部依存ゼロ・テストあり │
│                                                              │
│   MLXChatCore       判断（ロジック）はすべてここ                │
│   MLXChatUpdater    自動アップデート（macOS）                   │
└─────────────────────────────────────────────────────────────┘
                          ▲ 参照される（一方向）
┌─────────────────────────┴───────────────────────────────────┐
│ Apps/               Xcode プロジェクトがビルドする層             │
│                                                              │
│   MLXChatEngine     MLX の唯一のラッパー ← MLX を import する    │
│                     のはこのディレクトリだけ                    │
│   MLXChatUI         SwiftUI（iOS と macOS で完全に共通）        │
│   iOS/ macOS/ cli/  各入口のエントリポイント                    │
└─────────────────────────────────────────────────────────────┘
```

入口は 4 つあります。**すべて同じ Core を通ります。**

| 入口 | 実体 |
| --- | --- |
| Swift ライブラリ | `MLXChatCore` をそのまま import |
| CLI | `mlxchat-cli chat / bench / models` |
| URL スキーム | `mlxchat://chat?prompt=…` |
| GUI | iOS / macOS アプリ |

## 3. 核心の原則 — 判断はどこに置くか

> **判断（judgment）は Core の純ロジックに置く。GUI とエンジンには置かない。**

「判断」とは、こういうものです。

- 会話履歴をどこまでモデルへ渡すか（`Conversation.promptMessages`）
- つまみの許される範囲（`GenerationParameters.validate`）
- この端末でそのモデルが動くか（`DeviceProfile`）
- 速度をどう集計するか（`GenerationStats` / `BenchmarkSummary`）
- 失敗をどう言い換えて、次に何をすべきと伝えるか（`ErrorDetails`）
- 思考と答えをどこで切り分けるか（`ReasoningSplitter`）

これを 1 か所に集めると、**4 つの入口の挙動が構造的に一致します**。GUI にだけ
ある機能や、CLI だけ違う既定値、といったものが生まれません。逆に言うと、
GUI にしか無い機能を作りたくなったら、それは Core に足すべき機能です。

判断が ViewModel に生えてきたら、それは Core へ下ろすサインです。

### 具体例: 「思考を履歴に混ぜない」

推論モデルの思考は `ChatMessage.reasoning` に、答えは `ChatMessage.text` に
入れます。この 1 つの決定だけで、

- モデルへ渡す履歴（`text` を読む）から思考が自動的に外れ、
- 書き出し（`Transcript`）も既定で答えだけになり、
- 保存された会話を読み直しても同じ

が同時に成立します。「思考を除く処理」を入口ごとに書く必要がありません。

## 4. MLX に触ってよい層をひとつに絞る

`Apps/MLXChatEngine/MLXChatEngine.swift` **だけ**が `MLXLLM` / `MLXLMCommon` /
`MLX` を import します。MLX の型（`ModelContainer` / `ChatSession` /
`GenerateParameters` / `Generation`）はこのファイルの外へ出しません。境界を越える
のは Core の値型（`ChatRequest` / `GenerationEvent` / `GenerationStats`）だけです。

理由は 3 つあります。

1. **MLX の API はよく変わる。** 影響範囲を 1 ファイルに閉じ込めます。
2. **MLX を import した瞬間、そのターゲットは Apple Silicon + Metal でしか
   ビルドできなくなる。** テストしたいロジックを巻き込みたくありません。
3. **この層にはテストが書けない。** GPU と数 GB の重みが要るからです。テストの
   書けない層に判断を置くと、その判断は永久に検証されません。

だから**エンジンには判断を置きません**。あってよいのは「MLX の型への写し替え」と
「MLX の呼び出し」だけです。

### 規約ではなく構造で守る

「Core は MLX を import しない」は、レビューで守るルールではありません。ルートの
`Package.swift` に MLX の依存が**無い**ので、Core が MLX に触れた瞬間に
`swift build` が落ちます。守り方を人間の注意力に頼っていません。

同じ考え方で、`Apps/` は SwiftPM パッケージの外に置いてあります。`Sources/` に
混ぜると SwiftPM のターゲットに引きずり込まれてしまうからです。

## 5. メモリ — iPhone で落ちないための設計

**これがこのアプリで最も気を使っている部分です。**

iOS はアプリごとにメモリの上限があり、超えると**警告なしにプロセスを終了させ
ます**（jetsam）。MLX の重みは GPU から見えるメモリ（ユニファイドメモリ）に載る
ので、この上限にそのまま数えられます。つまり「大きいモデルを選ぶ」＝「アプリが
突然消える」です。

対処は 4 つ組み合わせています。

| 仕組み | 何をするか |
| --- | --- |
| `DeviceProfile` | 搭載メモリ × 係数（iOS 0.50 / macOS 0.70）で予算を出す |
| `ModelCatalog.requiredMemoryBytes` | 各モデルの必要量を**多めに**見積もる |
| `MLXChatEngine.applyMemoryLimits` | MLX のキャッシュ上限を予算の 1/4 に抑える |
| `kvBits` / `historyMessageLimit` | 会話が伸びたときの逃げ道を利用者に渡す |

係数の根拠:

- **iOS 0.50** … jetsam の実測下限側に寄せています。落ちるより「小さいモデルを
  勧める」ほうがましなので、楽観側には振りません。
- **macOS 0.70** … 残りを OS と他アプリに残します。ここを欲張ると重みがスワップに
  落ち、「動くけれど使い物にならない」状態になります。

見積もりを多めにするのも同じ理由です。**落ちるより「出さない」ほうがまし**です。

ただし、動かない見込みのモデルも**選べる**ようにしてあります。見積もりは概算で、
実機のほうが強いことがあるからです。警告は出しますが、最終判断は利用者に残します。

長い会話では KV キャッシュが重みより大きくなります。`kvBits`（4/8）と履歴の
上限が主要な逃げ道で、どちらも設定画面に出してあります。「iPhone で会話が続かなく
なったら、まず KV を 8bit に」が実用上いちばん効く操作です。

### なぜ別プロセスにしないのか

姉妹リポジトリ `min-nano/photogrammetry` は、生成をヘルパープロセスへ追い出して
います。RealityKit が内部エラーで `abort()` することがあり、同一プロセスだと
GUI ごと落ちるからです。

MLX は `abort()` しません。危険なのはメモリ不足による OS 側の強制終了で、これは
**プロセス境界では防げません**（子プロセスも同じ上限に数えられ、しかも GUI と
合わせて 2 つぶんのメモリを使います）。防ぐ手段は事前に避けること（`DeviceProfile`）
と減らすこと（`kvBits`）です。だから構成を単純に保っています。

### エンジンはプロセスに 1 つ

`MLXChatEngine.shared` の 1 インスタンスをチャット画面とベンチマーク画面で共有
します。別々に持つと同じ重みを二重に読み込むことになり、数 GB × 2 を抱えます。
節約ではなく必須です。

## 6. 思考（reasoning）の切り分け

Qwen3 / SmolLM3 / DeepSeek-R1 系は、答えの前に思考を `<think> … </think>` で
囲んで出します。そのまま流すと 3 つのことが同時に起きます。

1. 答えが数百トークン先まで出てこないように見える
2. 会話ログが思考で埋まる
3. **次の生成でその思考を履歴として食べさせてしまう**（コンテキストを浪費し、
   品質も落ちる）

なので受け取った時点で切り分け、`text`（答え）と `reasoning`（思考）に分けて
持ちます。画面では思考を折りたたんで出します（考えている間は自動で開き、答えが
出たら畳む。ただし手で操作したらそちらを優先）。CLI では思考を標準エラーへ流す
ので、`mlxchat-cli "…" > answer.txt` は答えだけを取れます。

### 難しいのはストリーミング

トークンは 1〜数文字ずつ届くので、`<think>` が `<th` と `ink>` に割れて届きます。
素朴に「届いた断片にタグが含まれるか」で見ると、割れたタグがそのまま本文に出ます
（画面に `<thi` というかけらが現れる）。

`ReasoningSplitter` は、**タグの接頭辞になりうる末尾だけを保留し、確定した部分
だけを返す**形にしてあります。生成の最後に `flush()` を呼ぶと、保留していた
「結局タグではなかった文字列」が本文へ戻ります。

全文を一度に切り分ける `split(_:)` も、内部で同じ逐次処理を回しています。
実装を 2 つに割らないためで、「画面の表示と保存済みの本文が食い違う」という
壊れ方を構造的に防いでいます。テストは 1 文字ずつ食わせた結果と全文を渡した
結果が一致することを確かめています。

> **ベンチマークの注意**: 推論モデルでは生成トークンの大半が思考です。tok/s は
> 素直に速度を表しますが、「答えが出るまで」は思考の長さに強く依存します。
> モデル間で比較するときはこの差に注意してください。

### 壊れたタグの並びに耐える

最初は「思考の外にいるなら `<think>` を、中にいるなら `</think>` を探す」という
実装でした。素直ですが、**閉じているのに `</think>` が来た場合を見落とします**。
壊れかけの小さいモデルは実際にこれを出します（実機で見たのは、思考を一度
閉じたあと、答えの中にもう一度 `</think>` が現れる形）。片方しか探していないと
そのタグは「ただの文字列」として本文に出てしまいます。

いまは**どちらの状態でも両方のタグを探し、先に現れたほうで状態を決めます**。
閉じているものをもう一度閉じても、開いているものをもう一度開いても、状態が
変わらないだけで害はありません。大事なのは「タグは状態を決めるためのもので、
本文にも思考にも出さない」という一点です。

割れたタグの保留も両方について取ります。`</th` は `<think>` の接頭辞では
ないので、開きタグだけを見ていると、外側で割れて届いた閉じタグを取りこぼします。

> **直せないもの**: タグの漏れは直せますが、**答えそのものの品質はモデル次第**
> です。小さいモデル（0.6B 級の 4bit）は同じ行を繰り返したり、途中で英語に
> 戻ったりします。上限（`maxTokens`）に達して答えに辿り着かないのも同じ理由で、
> こちらは設定で上限を増やすか大きいモデルへ替える以外にありません。

### 前後の空白を落とす

推論モデルは `</think>` のあとに改行を 2 つ置いてから答えを書き始めます。素直に
流すと吹き出しの先頭に**空行**ができ、答えが 1 行ぶん下がって見えます（実機で
見えました）。末尾の改行も同じように余白を作ります。

ところが、ストリーミングでは「いま届いた断片が最後か」が分かりません。
`trimmingCharacters(in: .whitespacesAndNewlines)` を最後に掛ける手は使えない
（最後がいつか分からない）し、画面側で掛けると保存済みの本文と食い違います。

そこで `ReasoningSplitter` の中で、

* 空白以外をまだ 1 文字も出していない間は、**先頭の空白を捨てる**
* 末尾の空白は**保留**し、次に空白以外が来たときに一緒に出す

としています。保留のまま生成が終われば、その空白は出ないまま消えます。結果は
`trimmingCharacters` と同じですが、**途中経過の見え方が最終形と食い違わない**の
が違いです。間の空白（段落の区切り）はそのまま残ります。

本文と思考のそれぞれに同じ規則を適用しているので、「考えた過程（N 文字）」の
文字数も余分な改行を数えません。

### 開閉は自動でやらない（`ReasoningDisclosure`）

思考は畳んで見せますが、**開閉が変わるのは利用者が操作したときだけ**です。
最初は「考えている間は開く・答えが出たら畳む」という自動の切り替えを入れて
いました。待ち時間に何が起きているか見えるので良さそうに思えたのですが、実機で
壊れました。

* 思考は数千文字になります。開いた吹き出しは画面数枚ぶんの高さになります。
* 履歴はトークンが届くたびに末尾へ寄せ続けています（そうしないと、伸びていく
  本文が画面の外へ出ていってしまう）。
* 答えの最初のトークンが届いた瞬間に自動で畳むと、**その高さが一度に消えます**。
  寄せる先は縮む前の座標のままなので、内容よりずっと下へ飛び、画面が真っ黒に
  なります。しかも一度飛ぶと、以降のトークンで寄せ直そうとしても目標の行が
  `LazyVStack` の描画範囲の外に居るため戻ってきません。

直し方は 3 つ重ねてあります。

1. **自動で縮めない。** 開閉の記憶は `ReasoningDisclosure`（Core・純ロジック）が
   持ち、既定は畳んだまま。利用者が開いたら生成が終わっても畳みません。
   高さが不連続に変わる瞬間そのものを無くすのが、いちばん確実な直し方でした。
2. **記憶を行（`MessageRow`）の `@State` に置かない。** `LazyVStack` は画面外へ
   出た行の状態を捨てることがあります。捨てられると開いていた思考が勝手に
   畳まれ、同じ「高さが一度に消える」が起きます。だから会話と同じ寿命の場所
   （ViewModel が持つ Core の値）へ移しました。
3. **寄せる先を高さゼロの目印にする。** 履歴の一番下に 1pt の透明な目印を置き、
   常にそこへ寄せます。発言そのものを目標にすると、高さが刻々と変わるうえに
   画面外では消えているので、寄せた先が内容より下になり得ます。目印は必ず
   内容の終わりに居るので、「そこへ寄せる」は「内容の終わりへ行く」と同義です。
   追従にアニメーションを付けないのも同じ理由で、目標が毎トークン動くため
   滑らせると着く前に次の指示が来ます。

つまり **UI の状態も「判断」なので Core に置く**、という第 3 節の原則が、
ここでは見た目の好みではなく不具合の直接の原因として現れています。

### 履歴は「交互」でなければならない

チャットテンプレートは Jinja で書かれていて、モデルごとに前提が違います。
Gemma 3 のテンプレートには次の行があります。

```jinja
{%- if (message['role'] == 'user') != (loop.index0 % 2 == 0) -%}
    {{ raise_exception("Conversation roles must alternate user/assistant/user/assistant/...") }}
```

つまり **user と assistant が交互に並んでいなければ、生成そのものが例外で
落ちます**（Qwen3 や Llama のテンプレートはここまで厳しくないので、同じ会話でも
問題なく動きます。だから「あるモデルだけで失敗する」という形で表面化します）。

会話は簡単に崩れます。生成が失敗すると**答えの無い user 発言が残り**、送り直すと
user が 2 つ続きます。実機で踏んだのはこの形でした。停止したときの「本文が空の
assistant」も同じ種類の残骸です。

そこで `Conversation.alternatingHistory` が、モデルへ渡す直前に履歴を整えます。

1. 中身の無い発言と system 発言を捨てる
2. 同じ役割が続いたら最後の 1 つだけ残す
3. assistant で始まらないようにする
4. **user で終わらないようにする** — 履歴の後ろには必ず今回の prompt（user）が
   続くので、user で終わっていればそこで 2 つ並ぶ

`ChatRequest.promptHistory` がこれを通した結果で、エンジンはそれを使います。
入口（GUI / CLI / URL / ライブラリ）に関係なく同じ規則がかかるのはこのためです。
「テンプレートの前提に合わせる」は**判断**なので、MLX を触る層ではなく Core に
置いています。

残骸そのものは `Conversation.removeFailedExchange` が消します。整えるだけでは
モデルは守れても、画面には同じ問いが 2 つ並んだままになるからです。

## 7. 外部連携の語彙をひとつに定義する

`APICommand` が、URL スキームと CLI 引数の**唯一の**定義です。パラメータ名
（`model` / `prompt` / `system` / `temperature` / `topP` / `maxTokens` /
`kvBits` / `history` / `runs` / `warmup`）も、コマンド名（`chat` / `bench` /
`models`）も、ここにしかありません。

逆変換（`Request` → CLI 引数）も同じファイルに置き、往復がテストで固定されて
います。これは GUI の「いまの設定を CLI で再現するコマンド」表示にも使っていて、
語彙が 1 つであることの実利になっています。

`APICommand` はファイルシステムにもネットワークにも触れません。だから単体テストは
文字列だけで書けます。

## 8. 何をどこへ保存するか

| もの | 置き場所 | 理由 |
| --- | --- | --- |
| 会話 | Application Support | **消えては困る**。キャッシュは OS が予告なく消す |
| モデルの重み | Caches | **消えてもよい**（再ダウンロードで復旧できる）。数 GB を消せない領域に置くべきではない |

会話は 1 会話 = 1 JSON ファイルにしています。1 ファイルにまとめると、生成のたびに
全会話を書き直すことになり、会話が増えるほど「1 トークン届くたびの保存」が重く
なります。分けておけば更新は当該ファイルだけで済み、壊れたファイルが 1 つあっても
他が読めます（読めないファイルは黙って飛ばす — 起動できないアプリにしないため）。

モデルの置き場所は `MLXLMCommon` の `defaultHubApi` に合わせてあります
（`Caches/models/<owner>/<name>`）。ここを間違えると「ダウンロード済みなのに一覧に
出ない」「消したのに減らない」が起きるので、組み立て規則は `ModelStorage` の
1 か所だけに置いています。

「ダウンロード済みか」の判定は、ディレクトリの有無ではなく `.safetensors` の
有無で見ます。ダウンロード中断の残骸で空のディレクトリができることがあり、それを
「済み」と誤判定すると、オフラインで開いたときに読み込みが失敗するまで気づけません。

## 9. テスト戦略

**`swift test` は MLX をビルドしません。** だから数十秒で終わります。

これは偶然ではなく、`Sources/` を外部依存ゼロの SwiftPM パッケージに保っている
ことの直接の結果です。MLX（C++ と Metal カーネルを丸ごとソースからビルドする）を
ルートの `Package.swift` に足すと、この性質は失われます。**足してはいけません。**

| 対象 | どうするか |
| --- | --- |
| 純ロジック（`APICommand` / `validate` / `DeviceProfile` / `BenchmarkSummary` / `ReasoningSplitter` / `UpdateFeed` …） | `swift test` で常時テスト |
| MLX を叩く層 | 自動テストしない（GPU と数 GB の重みが要る） |
| GUI（ViewModel） | 専用テストを置かない（判断を持たないので） |
| ネットワーク I/O（`UpdaterService`） | 自動テストしない・カバレッジからも除外 |

CI 上で MLX の挙動を見たいときは `ci-debug` ワークフロー（`workflow_dispatch`
専用）を使います。`build.yml` に一時的な調査ステップを挿してはいけません
（戻し忘れる・その commit が dev プレリリースとして公開される）。

カバレッジは PR に表として投稿され、しきい値未満なら**レポート側のジョブだけ**が
失敗します。計測とレポートを分けているのは、「テストが壊れた」のか「しきい値を
下回った」のかを一目で区別するためです。

## 10. ビルドとリリース

### なぜ Xcode プロジェクトが要るのか

iOS の `.app` は SwiftPM だけでは作れません（`swift build` が作るのは素の実行
ファイルで、バンドル・Info.plist・アセットカタログの面倒は見ません）。両 OS の
アプリを同じ手順でビルドするには `xcodebuild` が要り、そのためにプロジェクト
ファイルが要ります。

### なぜ `.xcodeproj` をコミットしないのか

`.pbxproj` は差分が読めず、競合が解決できず、Xcode が勝手に書き換えるからです。
原本は人が読める `project.yml` で、`scripts/generate-xcodeproj.sh`（XcodeGen）が
ローカルでも CI でも同じものを生成します。

### なぜアプリ 1 つ = 1 モジュールなのか

Core / Engine / UI を framework に分けていません。分けると iOS の埋め込みと署名の
手間が増えるわりに、依存の向きの強制は結局 `Package.swift` 側で効くからです
（第 4 節）。この構成の帰結として、`Apps/` のソースに `import MLXChatCore` は
**書きません**（同じモジュールなので不要かつコンパイルエラーになります）。

### リリースの形

| 契機 | タグ | 種別 |
| --- | --- | --- |
| `main` への push | `stable` | 正式（ローリング） |
| PR への push | `dev-<slug>` | プレリリース（ローリング） |
| ブランチ削除 | — | `cleanup-dev-release.yml` が掃除 |

「ローリング」は、同じタグを削除して作り直すという意味です。したがって自動
アップデートの判定は「より新しいか」ではなく「**コミットが違うか**」で行います
（`UpdateFeed.updateAvailable`）。

アプリの `Info.plist` には `GitCommit` / `GitBranch` / `BuildChannel` /
`BuiltAt` がスタンプされ（`scripts/stamp-app.sh`）、リリース本文の
`channel=` / `branch=` / `commit=` / `built=` 行と突き合わせます。

### テストとビルドを分けてある理由

`test.yml` と `build.yml` は `needs` で繋がっておらず、**並列に走ります**。
ビルド（片側 10〜30 分）の結果を待たずにテスト（数十秒）の結果が見え、テストの
結果を待たずにビルドが進みます。合否は branch protection の required checks 側で
見ます。

### 署名について

Apple Developer 証明書を CI に置かない方針です。結果として:

- **macOS 版**は ad-hoc 署名（`codesign --sign -`）。Apple Silicon はすべての
  Mach-O に署名を要求するので、これは必須です。公証はしていないので初回起動時に
  Gatekeeper の回避操作が要ります。
- **iOS 版の `.ipa` は未署名**。そのままでは iPhone に入りません
  （[install-ios.md](install-ios.md) を参照）。`xcodebuild -exportArchive` は
  署名を要求するので使えず、`scripts/package-ipa.sh` が `Payload/` に `.app` を
  入れて zip しています。

署名を切る指定は **`scripts/xcode-build.sh` のコマンドラインにしか置きません**。
`project.yml`（＝プロジェクトの性質）に書くと、手元の Xcode から自分の Apple ID
で実機へ入れることができなくなります — iOS は未署名アプリのインストールを拒否
するからです。署名を切るのは「証明書を持たない CI でビルドする」という**その
呼び出しの都合**であって、プロジェクトの性質ではありません。

### iOS に自動アップデートが無い理由

アプリが自分自身を差し替えられないからです（署名済みバンドルを OS が管理して
います）。更新の**判定**（`UpdateFeed`）は macOS と共通ですが、差し替え
（`UpdaterService`）だけが macOS 限定です。

## 11. 意図的にやらなかったこと

設計は「やらないと決めたこと」のほうが伝わりにくいので、明示しておきます。

| やらないこと | 理由 |
| --- | --- |
| 生成を別プロセスにする | MLX は `abort()` しない。OOM はプロセス境界では防げない（第 5 節） |
| Core / Engine / UI を framework に分ける | iOS の埋め込みと署名の手間に見合わない（第 10 節） |
| macOS をユニバーサルビルドにする | MLX は Apple Silicon 専用。Intel 向けを作っても動かない |
| iOS シミュレータ対応 | MLX が Metal の GPU family を要求するため動かない |
| 実際の生成を自動テストする | CI ランナーの GPU 要件が保証されず、重みが数 GB（第 9 節） |
| モデル id を自由入力にする | 非対応アーキテクチャは数 GB 落とした**後**に失敗する。サイズと必要メモリも分からず、動くかの判断ができない |
| 「タイトルを付ける」ためにモデルを呼ぶ | ローカル実行では高すぎる（数秒〜数十秒＋発熱＋電池）。最初の発言から機械的に決める |
| 外部依存を増やす | MLX とその推移依存だけにとどめる。バージョンは `project.yml` で固定 |

## 12. 「対」になっているもの

**片方だけを変えると壊れる**組み合わせです。触るときは必ず両方（とテスト）を
一緒に直してください。

| A | B | 壊れ方 |
| --- | --- | --- |
| `UpdateFeed.appAssetName` / `ipaAssetName` | `build.yml` のアセット名 | 自動アップデートが「アセットの無いリリース」として黙って無視する |
| `UpdateFeed` の `key=value` 解釈 | `build.yml` の notes.txt | 同上 |
| `build.yml` の `dev-<slug>` 生成規則 | `cleanup-dev-release.yml` の slug 規則 | プレリリースが孤児になる |
| `APICommand.parse` | `APICommand.arguments(for:)` | GUI が出す「CLI で再現するコマンド」が動かない |
| `UpdaterService` が探す `install-update.sh` | `project.yml` の resources 指定 | 自動アップデートが「アプリバンドルではない」と言って止まる |
| `ModelStorage.directory(for:)` | `MLXLMCommon` の `defaultHubApi` | ダウンロード済みなのに一覧に出ない／消しても減らない |
| `scripts/xcode-build.sh` | `build.yml` と `ci-debug-job.sh` | 「CI では通るが調査では落ちる」（逆も） |
| `scripts/xcode-build.sh`（署名しない・CI 用） | `scripts/run-ios.sh`（署名する・手元用） | 1 本にまとめると「CI で署名してしまう」「手元で署名し忘れる」がどちらも起こる。分けたまま保つこと |
| `project.yml`（署名を切る指定を**書かない**） | `scripts/xcode-build.sh`（切るのはここだけ） | project.yml 側に書くと、手元の Xcode から実機へ入れられなくなる（未署名アプリは iOS が拒否する） |
| カバレッジの除外リスト | 「その層に判断を置かない」という約束 | 除外した層に判断が溜まっても誰も気づかない |
